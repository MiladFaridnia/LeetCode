مفهوم کلیدی: پیچیدگی زمانی (Big-O) و تحلیل کاراییتحلیل کارایی · Time Complexity

پیچیدگی زمانی (Time Complexity) سنجش ثانیه‌ها با کرونومتر نیست؛ بلکه سنجش نرخ رشد تعداد عملیات کامپیوتر با افزایش حجم ورودی (n) است.

💡 مثال ملموس: پیدا کردن یک نام در دفترچه تلفن ۱ میلیون نفره (n = 1,000,000)
• جستجوی خطی (O(n)): ورق زدن صفحه به صفحه از ابتدا تا انتها ➔ در بدترین حالت ۱,۰۰۰,۰۰۰ مقایسه!
• جستجوی دودویی (O(log n)): باز کردن از وسط و حذف نیمی از گزینه‌ها در هر گام ➔ فقط ۲۰ مقایسه!
۱. O(1) · ثابت
دسترسی مستقیم با اندیس arr[i] یا کلید Hash Map. مستقل از حجم داده (۱ عملیات).
۲. O(log n) · لگاریتمی
جستجوی دودویی؛ نصف شدن داده‌ها در هر گام. جهش سرعت در ورودی بزرگ (۲۰ گام برای ۱M).
۳. O(n) · خطی
یک حلقه ساده پیمایش آرایه. رشد عملیات مستقیماً و همگام با اندازه ورودی (n گام).
۴. O(n log n) · شبه‌خطی
مرتب‌سازی‌های بهینه (Merge Sort و sort() پیش‌فرض). حدود ۲۰M عملیات برای ۱M داده.
۵. O(n²) · درجه دو
دو حلقه تودرتو (Brute Force). مقایسه تمام جفت‌ها؛ برای ورودی‌های بالای ۱۰K سریعاً TLE می‌گیرد.
قانون طلایی ۱۰ به توان ۸ (مرز پذیرش در لیت‌کد)

یک پردازنده در هر ثانیه حدود 10⁸ عملیات انجام می‌دهد. اگر طول ورودی n = 10⁵ باشد:
• روش O(n): فقط 10⁵ عملیات ➔ ۰.۰۰۱ ثانیه (Pass ✅)
• روش O(n²): 10¹⁰ عملیات ➔ حدود ۱۰۰ ثانیه (Time Limit Exceeded ❌)

تله ارزیابی: فقط کار کردن کد کافی نیست!

پرسشگر بلافاصله می‌پرسد: «Big-O کدت چقدر است و چطور آن را کاهش می‌دهی؟»
کدی که خروجی درست بدهد اما در ورودی‌های بزرگ زمانش به پایان برسد (TLE)، کاملاً غیرقابل‌قبول است.

«تسلط بر Big-O به شما شهود مهندسی می‌دهد تا پیش از نوشتن حتی یک خط کد، تشخیص دهید کدام ایده به پاسخ بهینه می‌رسد و کدام به بن‌بست خواهد خورد.»

مهندس تحلیل‌گر (با درک منطق و چرایی)

دلیل را می‌فهمد: «چون آرایه مرتب است، برای کم کردن مجموع، تنها راه این است که بزرگ‌ترین عدد را برداریم و عدد کوچک‌تری از سمت راست انتخاب کنیم (R--).»

⚡ تست پرسشگر (تغییر صورت مسئله)
پرسشگر می‌گوید: «اگر آرایه نزولی مرتب شده بود چه؟»
• کاندیدای حفظ‌کننده: کاملاً قفل می‌کند چون کدی که حفظ کرده دیگر کار نمی‌کند!
• فردی که چرایی را فهمیده: در ۲ ثانیه متوجه می‌شود جهت حرکت اشاره‌گرها معکوس می‌شود.
🎯 ۳ سوال طلایی که بعد از هر مسئله باید بپرسید:
۱. چرا این ساختار داده؟ چرا اینجا Hash Map جواب داد ولی لیست عادی کند بود؟
۲. چرا این جهت حرکت؟ منطق ریاضی پشت جلو یا عقب رفتن متغیرها چیست؟
۳. اگر فرضیات عوض شوند؟ اگر اعداد منفی باشند یا آرایه تکراری باشد چه؟

«وقتی چرایی عملکرد یک الگوریتم را بفهمید، آن ایده برای همیشه در ذهنتان تثبیت می‌شود و هیچ سوال جدیدی نمی‌تواند شما را غافلگیر کند.»

گلوگاه روش‌های مستقیم و خام (نگاه به آینده)

در هر عنصر می‌ایستیم و برای یافتن جفت یا مکمل، کل بقیه آرایه را با حلقه دوم جستجوی خطی O(n) شخم می‌زنیم. برای ۱۰,۰۰۰ ورودی ➔ ۵۰ میلیون عملیات و خطای قطعی TLE!

تغییر پارادایم با پرسیدن «چرا؟» (حافظه گذشته)

چرا به جای شخم زدن آینده، یک «دفترچه یادداشت گذشته (Seen Map)» نداشته باشیم؟ در هر خانه فقط می‌پرسیم: «آیا مکمل من قبلاً گذشته و ثبت شده است؟»

چرا جدول درهم‌سازی (در کاتلین: MutableMap / HashMap) معجزه می‌کند؟

در آرایه برای جستجو باید تک‌تک خانه‌ها بررسی شوند (O(n))؛ اما در Hash Map، تابع هش مقدار کلید (Key = عدد) را مستقیماً به نشانی حافظه نگاشت می‌کند. در نتیجه، استعلام «آیا این کلید هست؟» در میانگین زمان O(1) انجام می‌شود!

روش اول: راه‌حل ساده و مستقیم (Brute Force)روش اولیه · Brute Force

در جلسه ارزیابی، همیشه بیان راه‌حل اولیه (Brute Force) اولین گام است تا نشان دهید مسئله را کامل فهمیده‌اید.

fun twoSumBruteForce(nums: IntArray, target: Int): IntArray {
    val size = nums.size

    // حلقه اول: یک عدد را برمی‌داریم
    for (i in 0 until size) {
        val firstNumber = nums[i]

        // حلقه دوم: در خانه‌های بعدی به دنبال عدد دوم می‌گردیم
        for (j in (i + 1) until size) {
            val secondNumber = nums[j]

            // آیا جمع این دو عدد برابر با هدف است؟
            val sum = firstNumber + secondNumber
            if (sum == target) {
                return intArrayOf(i, j)  // پاسخ پیدا شد!
            }
        }
    }

    return intArrayOf()  // اگر هیچ جفتی پیدا نشد
}

تحلیل پیچیدگی:

  • پیچیدگی زمانی: O(n²) — تعداد مقایسه‌ها برابر است با n*(n-1)/2.
  • پیچیدگی فضایی: O(1) — هیچ حافظه کمکی اضافه‌ای استفاده نمی‌شود.
چرا این راه‌حل در لیت‌کد رد می‌شود؟ وقتی طول آرایه به 10⁴ می‌رسد، تعداد عملیات به حدود ۵۰ میلیون می‌رسد که منجر به خطای Time Limit Exceeded (TLE) می‌شود.

پیاده‌سازی تمیز و خط به خط کد بهینه (Kotlin)کدنویسی تمیز · Clean Code

پیاده‌سازی تک‌پیمایشی (One-Pass Hash Table) با زبان Kotlin با ساختار کاملاً شفاف، گام‌به‌گام و قابل فهم:

fun twoSum(nums: IntArray, target: Int): IntArray {
    // دفترچه یادداشت: ذخیره اعدادی که قبلاً ملاقات کرده‌ایم
    // کلید (Key) = مقدار خود عدد | مقدار (Value) = اندیس آن عدد در آرایه
    val seen = mutableMapOf<Int, Int>()

    // پیمایش تک‌تک خانه‌های آرایه از ابتدا تا انتها
    for (i in 0 until nums.size) {
        val currentNumber = nums[i]

        // محاسبه مکمل: چه عددی کم داریم تا جمعش با عدد فعلی بشود target؟
        val neededNumber = target - currentNumber

        // آیا این مکمل را قبلاً دیده‌ایم و در حافظه داریم؟
        if (seen.containsKey(neededNumber)) {
            val complementIndex = seen[neededNumber]!!
            return intArrayOf(complementIndex, i)  // جفت هدف پیدا شد!
        }

        // اگر مکمل نبود، عدد فعلی و اندیسش را برای مراحل بعد یادداشت می‌کنیم
        seen[currentNumber] = i
    }

    return intArrayOf()  // اگر هیچ جفتی پیدا نشد
}

تحلیل نکات ظریف پیاده‌سازی و خوانایی:

  • تفکیک صریح متغیرها: استخراج عدد جاری (currentNumber)، محاسبه مکمل (neededNumber)، و خواندن اندیس مکمل (complementIndex) هرکدام در یک خط مستقل انجام شده تا جریان منطق کاملاً شفاف باشد.
  • جستجوی O(1) با containsKey: با این متد در زمان ثابت چک می‌کنیم آیا کلید مکمل در جدول هش وجود دارد یا خیر (در کاتلین فرم neededNumber in seen نیز معادل آن است).
  • عدم تکرار یک عنصر: چون عدد فعلی بعد از شرط در Map درج می‌شود، ناممکن است که یک عنصر با خودش جمع شود.
  • پیچیدگی نهایی: زمان O(n) (یک بار پیمایش آرایه) · حافظه O(n) (ذخیره عناصر در HashMap).

پیاده‌سازی تمیز در کاتلین: Two Sum II (دو نشانگر) کدنویسی تمیز · Clean Code 🔗 LeetCode #167

پیاده‌سازی الگوریتم Two Pointers با تفکیک صریح متغیرها و ساختار شفاف و خوانا در کاتلین:

fun twoSum(numbers: IntArray, target: Int): IntArray {
    // دو نشانگر در ابتدا و انتهای آرایه مرتب‌شده
    var leftIndex = 0
    var rightIndex = numbers.size - 1

    // حرکت همگرای نشانگرها به سمت یکدیگر تا لحظه برخورد
    while (leftIndex < rightIndex) {
        val currentSum = numbers[leftIndex] + numbers[rightIndex]

        when {
            currentSum == target -> {
                // مسئله ۱-محور است؛ بنابراین ۱ واحد به هر اندیس اضافه می‌کنیم
                return intArrayOf(leftIndex + 1, rightIndex + 1)
            }
            currentSum < target -> {
                // جمع کوچک‌تر از هدف است؛ برای افزایش جمع، نشانگر چپ را جلو می‌بریم
                leftIndex++
            }
            else -> {
                // جمع بزرگ‌تر از هدف است؛ برای کاهش جمع، نشانگر راست را عقب می‌آوریم
                rightIndex--
            }
        }
    }

    return intArrayOf()  // طبق صورت مسئله هرگز به این خط نمی‌رسد
}

تحلیل پیچیدگی و نکات طراحی کد:

  • تفکیک نام‌ها و وضوح خوانش: استفاده از نام‌های شفاف leftIndex، rightIndex و currentSum به جای حروف اختصاری مبهم، خوانایی را تضمین می‌کند.
  • ساختار ساخت‌یافته when: تصمیم‌گیری سه‌گانه (برابری، کوچکتری، بزرگتری) به جای if-else تو در تو، خوانش منطق را برای بررسی‌کننده کد دلپذیر می‌سازد.
  • پیچیدگی زمانی: O(n) — در هر دور حلقه، حداقل یکی از دو نشانگر یک گام جابجا می‌شود؛ بنابراین حداکثر n مقایسه انجام می‌گیرد.
  • پیچیدگی فضایی: O(1) — هیچ ساختار داده یا آرایه کمکی تولید نمی‌شود و قید سخت‌گیرانه مسئله کاملاً رعایت شده است.

پیاده‌سازی اصولی با زبان Kotlin با رعایت کامل مدیریت تکرارها و تفکیک نام متغیرها:

fun threeSum(nums: IntArray): List<List<Int>> {
    val result = mutableListOf<List<Int>>()
    nums.sort()  // مرتب‌سازی در زمان O(n log n)

    for (i in 0 until nums.size - 2) {
        val firstNum = nums[i]

        // بهینه‌سازی: اگر کوچک‌ترین عدد مثبت باشد، جمع سه عدد هرگز صفر نمی‌شود
        if (firstNum > 0) break

        // جلوگیری از تکرار: اگر عدد اول با قبلی یکی بود، از آن عبور کن
        if (i > 0 && firstNum == nums[i - 1]) continue

        var leftIndex = i + 1
        var rightIndex = nums.size - 1

        while (leftIndex < rightIndex) {
            val currentSum = firstNum + nums[leftIndex] + nums[rightIndex]

            when {
                currentSum == 0 -> {
                    result.add(listOf(firstNum, nums[leftIndex], nums[rightIndex]))

                    // پرش از عناصر تکراری هم‌جوار در سمت چپ
                    while (leftIndex < rightIndex && nums[leftIndex] == nums[leftIndex + 1]) {
                        leftIndex++
                    }
                    // پرش از عناصر تکراری هم‌جوار در سمت راست
                    while (leftIndex < rightIndex && nums[rightIndex] == nums[rightIndex - 1]) {
                        rightIndex--
                    }

                    leftIndex++
                    rightIndex--
                }
                currentSum < 0 -> leftIndex++   // جمع کوچک است؛ حرکت به سمت اعداد بزرگ‌تر
                else -> rightIndex--            // جمع بزرگ است؛ حرکت به سمت اعداد کوچک‌تر
            }
        }
    }

    return result
}

تحلیل پیچیدگی و ظرافت‌های مهندسی:

  • پیچیدگی زمانی: O(n²) — مرتب‌سازی در O(n log n) انجام می‌شود و حلقه بیرونی با الگوی Two Pointers درونی زمان O(n²) می‌گیرد؛ زمان کل O(n² + n log n) = O(n²) است.
  • پیچیدگی فضایی: O(1) — به جز لیست پاسخ، هیچ ساختار کمکی اضافی مانند Set یا Map استفاده نمی‌شود.
  • دو پرش هوشمند برای یکتایی کامل: بررسی firstNum == nums[i-1] در حلقه بیرونی، و پرش حلقه‌های داخلی پس از ثبت پاسخ، تضمین ریاضی برای عدم تکرار هر سه‌تایی ارائه می‌دهد.
